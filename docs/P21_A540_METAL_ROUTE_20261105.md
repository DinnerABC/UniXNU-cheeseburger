## Scope and result

**Confirmed offline implementation, not a working system Metal device.** The
21H461 AIR → NIR → IR3 compiler runs on this Mac, produces actual A540 machine
code and complete reflection, and refuses malformed/unsupported input. The
controlled userland adapter compiles for arm64 iOS17.7 and uses the unchanged
`package/BoardRuntime/NativeAdrenoABI.h`. No device, payload, firmware, kernel GPU
core, existing Metal plugin, Git commit, or system package was changed.

The main agent owns HANDOFF and hardware integration. The inherited device
state is root Recovery following Wagtail boot `0x3de7e608`; this work performs
**zero device operations** and cannot improve that boot's GPU result.

## Compiler interface and validation

The local executable is `native540-compiler`:

```sh
/Users/dinnerabc/unixnu-p21/native540/native540-compiler --list /path/to/input.metallib
python3 tools/gpu-native540/native540.py /path/to/input.metallib ENTRY /path/to/new-output-directory
```

`--list` reports names, Metal TYPE, AIR offsets and lengths. The compiler uses
SAGIT's structural archive parser, verifies the selected AIR SHA256, compiles
with `qgpu_compile_air_nir` and validates `GPU::JIT::valid` plus archive stage
identity. It does not send `QGPUProgramImage` to this board's kernel: SAGIT's
JIT version41/83784-byte format is **not NativeAdreno ABI**.

The stable Python wrapper snapshots the input, verifies compiler/backend pins,
runs a bounded subprocess, validates every output variant and atomically
publishes a new directory only on success. Existing directories are refused.
The output includes:

- `program.base.ir3`, plus independently allocated fragment MSAA and optional
  constant-window variants when returned by the compiler;
- `program.json` with fixed `gpu=540`, route, shader SHA256/length, source pins,
  builder and adapter hashes, input hash/length, timing, `targetOSBuild=21H461`,
  and `runtimeVerified=false`;
- all scalar allocation/resource fields, immediate values, and the complete
  **621 uint32 descriptionWords** (2484 bytes), including strides, varying
  semantics/registers, attributes, samplers, framebuffer and constant-window
  records, losslessly serialized in the pinned `GPUJITProtocol.h` field order.

`targetOSBuild` names the intended adapter profile, not a claim that an
arbitrary caller's library originated from that OS. Actual evidence below
comes from the read-only 21H461 mount. Consumers must use the recorded schema
and upstream pin; never infer offsets from 18.6 Metal `_limits` or a different
SAGIT revision. No `_limits` layout or MTLDevice class is copied here.

## Can A540 be added to Turnip?

It is possible in principle, but it is a new A5xx Vulkan hardware backend, not
an additional chip-ID entry. The pinned Turnip `tu_device.cc` admits generations
6, 7 and 8; the command/pipeline/descriptor/image paths rely on those generations.
Mesa's existing A5xx Gallium driver, register XML and IR3 backend are reusable
reference material, not an already available A540 Vulkan ICD.

Work includes A5xx descriptors and shader state, render and compute command
encoding, image layouts/formats, render passes and tile/GMEM paths, synchronization,
cache management, memory/import, feature reporting and conformance testing.
An initial sysmem/compute-only prototype can reduce scope but does not satisfy
metal2vulkan's Vulkan1.2/timeline prerequisites or system graphics workloads.
XNU also needs the existing Darwin KMD and NativeAdreno transport adapted; an
Android vendor ICD cannot be assumed portable to Darwin.

Rough engineering estimates, not measured schedules: an experienced full-time
GPU/Vulkan developer might reach limited compute/triangle proof in 2–6 months,
a useful Vulkan1.2 subset in 6–18+ months, and broad correctness/conformance in
12–24+ months. A solo developer learning both APIs and the hardware should budget
years and an uncertain completion date. Availability of working hardware,
firmware, debugging and upstream review changes these estimates substantially.
A successful Vulkan driver would still leave the target OS Metal private ABI,
IOSurface and compositor integration to implement.

For this project the direct SAGIT AIR/NIR/IR3 route avoids that additional ICD
project and already compiles genuine21H461 CS/VS/FS. Turnip A540 is a defensible
separate research goal, but is not the shortest route to Metal on this board.

## Controlled frontend and integration boundary

`NativeMetal540Client.{h,cpp}` consumes the existing ABI exactly. The owner
provides and serializes the existing transport callback. Query validates version
and bounds; allocation/map validate lengths/permissions; submit zeroes reserved
and unused slots, rejects overflowing spans, and returns real fences. Short
replies, failed submission or failed fence waiting quarantine the client and
never automatically free possibly DMA-owned BOs or reconnect.

`NativeMetal540EncodeBarrier` generates a real minimal A5xx WAIT_IDLE + NOP
stream in a caller-owned mapped BO. The owner cleans the BO cache before
Submit, retains BO/mapping/connection until successful WaitFence, and performs
any required invalidation before readback. The model proves wire sizes,
refusal, quarantine and packet bytes; no submission was attempted on hardware.

**Still blocked:** a shader-aware A540 pipeline/binding admission layer must
translate these compiler allocations, immediate/driver constants, resource
bounds and graphics-stage linkage into actual A5xx state. The existing kernel
constant compute-test header cannot consume arbitrary reflected output. This
adapter deliberately does not encode arbitrary shader dispatch/draw, create
sagit IOGPU classes, introduce selectors, supply Vulkan, or publish a system
Metal device. Public ABI Query alone does not prove GPU identity or successful
shader execution. Main agent must independently verify board540 identity and
service/runtime readiness before calling it. Neither successful compilation
nor barrier/fence progress proves rendered pixels.

Next coordinated step: use the stable CLI outputs as frozen shader inputs;
review `GPUShaderProtocol.h`/A540 `AdrenoPipeline.h` admission and state setup
against this board's real resource model; implement validated compute bindings
and execute a bounded readback test only after the core-drain/runtime blocker
is resolved. Preserve the current fail-closed system-device boundary until
real shader, synchronization and rendering outcomes pass.
