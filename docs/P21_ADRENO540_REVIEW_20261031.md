# P21 Adreno 540 审计与后续方向（2026-10-31）

本次为只读源码、离线产物与已回收日志审计；未启动设备、重新编译或写入分区。项目固定上游为 `.work/p21-official-framework`，同 SoC 对照为 `docs/upstream/reference/sagit/`，其代码与参数仍需按本机实际 SoC、SMMU 版本和系统配套核实。设备当前是否仍在 Recovery 需下次操作前重新枚举。

## 主要审计发现

1. **最新门禁记录不匹配当前镜像（高优先级）**：`out/p21/fb-qup3/uefi/boot-p21-up1.img` 实测 SHA-256 为 `aea9a9fa18d420614246ce29f027ea784729556a2f9f3d2742d15b5001570565`，与同目录 `uefi/packaging.json` 一致；但 `out/p21/fb-qup3/offline-gate.json` 仍指向 `a4af3b18...`、旧内核及 645 字节参数；`pins.json` 亦为旧值。不能使用这两份文件证明 `aea9...` 通过门禁或 pin 验证。即使其他运行日志另有通过记录，也必须定位其本轮记录并与镜像、固件、kernel、ADT、payload 哈希一一匹配。持续覆盖候选目录会丢失每轮对应关系，后续每轮单独命名、不可覆盖地保存所有证据。
2. **reset 失败路径可能遗留停流**：`package/BoardRuntime/CheeseburgerGpuCp.cpp` 的 `gpuReset` 先写 `kVBIFHalt=15`；若 ack 超时、idle 失败或其他后续检查失败则直接返回，未看到相应恢复。日志 `20261031T110117Z` 为 `stage=1 rc=-2 vbif=f000f`，与该潜在状态一致；不能据此证明实际引起了黑屏或卡死。必须对照 sagit/Linux 的设备所有权、排空及复位语义，设计失败清理和恢复（包含时钟/电源已消失的情况），再用 host 模拟覆盖各失败点；未验证之前不要在共享运行系统反复进行 CP reset。
3. **GPU 电源值是旧快照，并非 start 瞬时测量**：当前 `cheeseburger_gpu_cp_probe` 把 `cb_gpu` 之前的值复制到 `GCP7`，而不是在 begin 时读取。`cx/gx/gfx` 只能证明采样时的寄存器值，不能确认 reset 时或整个 8 秒期间仍上电。检查 cb_gpu 的真实采样时刻和电源域 bit 定义。
4. **五 buffer 映射不等于 DMA 验证**：实机 5 次 `r=0` 和 TLB 同步说明软件建表和同步例程报告成功；未用设备实际读取/写回验证页表、stream ID、缓存一致性和 DMA 可达性。`RBRead=0` 加 `WPTR=9` 证明这次没有观察到读取指针前进，不能单凭它断言微码一条指令也没执行、解释其根因或排除 MMIO 读数及复位问题。
5. **configure 的通过范围需要收紧**：`gpuStart` 只回读少量基址低字、ring control、计数及两个控制寄存器；不能称整个 configure 全部通过。须补高字、微码物理/设备地址、页表属性、TLB、固件版本与权属的有界核对，实际访问仍需设备 DMA 验证。
6. **PMRD 与 console 假设都未证实**：两轮日志中断不总发生在已记录的 PMRD 消息窗口，这削弱了简单的“恰逢该窗口”假设，但不能排除未记录的电源事件或其后效应。长 IOLog 与中断只具有小样本相关性；写入日志可能阻塞，也可能系统在 `IOSleep`、定时器、调度、内存或其他路径卡住。最后日志和最后持久快照是下界，不证明其后没有执行任何 GPU 写。上报中的“均无 GPU 写”应限定为：从代码顺序和已持久证据看，**未观察到 reset 写入，未能证明执行与否**。
7. **自动恢复与存活标记需要独立路径**：已证实最新轮由用户手动返回；未走完 400 秒自动回收路径。`CheeseburgerAutoReset.cpp` 在 SMC 前调用 `IOLog` 和 `IOSleep`，因此不能仅根据未重启断定 SoC 全停。把计数写到普通 RAM 但没有独立读取通道，不构成可观察的存活证明；重启后 RAM 留存也未经证实。把标记交给同一个 UFS writer 同样无法独立验证 writer。必须先确认可用的外部读取/持久路径及复位前后保持性；不要为诊断擅自写其他分区或随意改 MMIO。
8. **日志的冷状态不是全部相同**：报告声称 111210Z 冷状态与 103113Z 完全一致，但 `GCP2 st` 前者为 `0x80000101`，后者 `0x800001c1`；两者均 `me=303`，差值本身需结合采样时刻和定义分析。五个 retrieval 的 boot ID 与报告一致；持久窗口旧行仍需按 boot ID 与时间过滤。
9. **SCTLR 文字解释互相矛盾**：报告称 `0x1027` CFCFG=0，代码注释却写含 CFCFG；`0x1167` 增加哪些功能、置位后的 fault 行为，必须以本机适用的 ARM SMMU 实现寄存器定义逐 bit 解码并核对读回，不应把未验证的安全/容错语义当结论。0x1027 与 0x1167 的差值是 `0x140`。本地页表 walker 级移位为 39/30/21/12，与报告所述形式一致；硬件实际 TCR/VA 宽度和表属性、SID 路由尚需核实。
10. **仓库和分区范围审计仅部分完成**：`git status` 抽查干净、`git ls-files` 没有列出所查 GPU 固件及持久日志路径，不能单靠此证明仓库所有历史均无私有材料；misc/userdata 的具体写入边界与授权、原始设备回读及所有写命令未逐项审计，不能在本次 review 中认证“无其他写入”。保持现有限定，不新增存储写入。

## 目前证据能支持什么

- 五组日志 retrieval boot ID 与报告一致；`20261031T103113Z` 有显示传输和五个映射成功记录。
- `20261031T104613Z` `GCP5 stage=3 rc=-4 r=0 w=9`；源码中的 `gpuStart` 在检查条件不满足到超时后返回 -4。它证明此前 reset 返回 0、关键寄存器子集回读通过及 WPTR 指向 9；不是全套 CP/GPMU 或 Metal 成功。
- `20261031T112909Z` 只记录到 begin，8 条快照；用户说手动进 Recovery，设备执行停在哪里仍未证实。日志中的 `stage=1 rc=0` 属于预置状态，不是 reset 成功证据。
- 从本机 `AdrenoStartup.h` 对照，`packet7(0x48,8)` 和 8 个 init 字匹配；ring register 地址与初步值需继续对照具体头文件和 Linux 版本后逐项独立验算。本地实现 ring 字节清理与发布的顺序和参考存在差异，不能仅凭包头一致认为完整序列等价。
- 257 MHz 与黑屏的 A/B 是有价值的实机线索，但需确认两镜像的完整输入差异、设备状态和复现性，不能把单对实验扩展为所有黑屏都由该调频引起。保持 rate=0 基线。

## 建议优先顺序

1. **冻结现状与证据**：以 boot ID 建立不可覆盖的候选 manifest，保存 boot 命令、完整参数、输入/输出 SHA-256、实际 gate/EFI/FV 结果与存储读写收据；禁止引用旧 `offline-gate.json`、旧 `pins.json`。不要删除旧候选或覆盖持久 Data。
2. **构建离线审计**：对 reset 的每个失败点实现/验证符合真实 provider 所有权的清理设计；核对设备路径内 IOLog、IOSleep、PMRD、锁持有关系，特别是 reset worker 同步原语与执行上下文。用寄存器模拟验证清理顺序；如硬件状态不可读，采用明确失败停用而非伪造成功。
3. **先完成可观察性，再进行一次受控 A/B**：在用户允许后，使用已证明运行、互不冲突且可读取的独立通道区分调度、console、持久日志和自动恢复（先证明心跳通道在正常/故障下可读取）；优先考虑现有可观测接口，未证明保留性的 RAM、同一 UFS writer 或控制台本身不算独立证据。短/长行测试只改变该变量，禁用 CP 写与其他新动作；验证后再针对具体路径修复。
4. **恢复稳定 CP 诊断**：证实时钟及访问权限，清晰记录 reset 前后寄存器、超时路径、故障状态，验证 SMMU SID/CB/TCR/PTE/cache 和小范围可控 DMA；应在有一致性和故障隔离证据后才 kick。两种 SCTLR 的差异单独评估，不同时更改多个潜在变量。安全模式改动先对照本 SoC 的真实固件/ZAP 前提，切勿强制绕过保护以制造成功。
5. **分阶段推进图形栈**：确认 RPTR 前进和完成条件，再验证 GPMU firmware 反应与 fault；之后最小 DMA/fence、用户客户端，最后 Metal 与合成。每一阶段保留可复现输出、回滚入口及真实实机证据；仅能初始化并不等于可用 Metal。

历史报告关于时钟黑屏、PMRD、reset 和 `0xe00002c7` 的过度归因均以本审计和 `HANDOFF.md` 最新勘误为准。
