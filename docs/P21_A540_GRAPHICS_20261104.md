## Ported path

`package/BoardRuntime/CheeseburgerGpuBlit540.h` emits, into an ordinary
indirect buffer of the existing `Engine540`:

1. `restore()`: the A5xx linear/GMEM-bypass baseline (SP/RB/TPL1 64-bit
   addressing, UCHE invalidate, HLSQ update, PC/GRAS/RB/VPC/SP/TPL1 defaults,
   `RB_CCU_CNTL=0x10000000`, `RB_CNTL=BYPASS`), register for register from
   sagit `AdrenoPipeline.h:345-400`.
2. `begin2D()`: Mesa fd5 sysmem events 25 (CCU invalidate) and 24 (UCHE flush).
3. `solidFill()`: `CP_SET_MODE`/BLIT2D (`0x6c`=5), `RB_2D_*` destination
   registers with format 75 (RB5_R32_UINT), the solid source dwords, the
   `CP_BLIT` packet (`0x2c`) with pixel bounds, END2D (`0x6c`=8), then a color
   cache flush: `CACHE_FLUSH_TS` event 29 and `CP_WAIT_REG_MEM` on the sequence
   word. This is RB/GRAS/CCU work, not `CP_MEM_WRITE`.
4. The normal Engine540 completion timestamp fences the whole stream.

`package/BoardRuntime/A5xxRegs.h` is generated from Mesa
`src/freedreno/registers/adreno/a5xx.xml` with `gen_header.py` (the same
generator sagit uses). The local Mesa is 26.2; Mesa 26 merged
`RB_2D_SRC/DST_LO/HI` and `UCHE_CACHE_INVALIDATE_MIN/MAX` into `reg64`
entries, so the header keeps the older symbol names as aliases at the same
offsets. Nothing in the encoding depends on a newer field definition.

## Boot-time test (`cheeseburger-gpu-clear`, default on)

After the second ring keep-alive the probe:

1. allocates an 8 KiB IB page, a 64 KiB linear 256x64 RGBA8 target and a 4 KiB
   flush/wait page (all kernel-owned), zeroes them, and maps them at
   `0x2040000`, `0x2060000` and `0x2050000` **outside** `gSubmitLock`;
2. encodes one `restore()` and four 128x32 solid fills, one per quadrant, each
   with its own END2D and color flush;
3. submits through the verified `cheeseburger_gpu_engine_submit` path (pre-kick
   power check, TLBIALL, ATOS/kit leaf gate, fence) and reads the centre of
   each quadrant plus an edge sample with the CPU;
4. repeats the same engine for a 96-row band at the top of
   `PE_current_console()`, which is GPU-authored pixels on the panel without a
   CPU copy.

Results are logged as `CB GPU clear:` and persisted as the `CLR` line
(`rc/seq/words`, four pixels, edge, match, `ib/tgt` physical addresses, scanout
result). A failure keeps every page and mapping for the boot.

## Display handoff constraints (P21-Curlew/Dunlin)

Two measured constraints block a direct GPU scanout on this board:

| Constraint | Evidence | Consequence |
|---|---|---|
| Firmware GOP pitch is 4320 bytes (1080x1920, depth 32) | `prep=-5 pe=1080/1920/4320/32` (boot `0x40a26751`) | `RB_2D_*_SIZE.PITCH` counts 64-byte units; 4320 is not encodable, so the 2D engine cannot write the GOP buffer. |
| MDP5 `PIPE_SRC0_ADDR` is 32-bit in this path | A 1088x1920 frame allocated at `pa=0x111876000` (4.58 GiB) was rejected by the flip hook (boot `0x40a433bd`) | A GPU-filled full frame cannot be scanned by MDP until it is allocated below 4 GiB or the path is extended to the IOMMU. |

The kernel now records both facts and leaves the display untouched on failure.
The next path is sagit's compute fallback: an IR3 compute shader using
byte-addressed global stores can write the GOP buffer at its real pitch
(4320) without the 64-byte destination rule, which also avoids the 4 GiB MDP
limit because the writes go through the GPU SMMU address space.

## Compute shader attempt (P21-Egret/Gannet)

Mesa 26.2's IR3 assembler produces a5xx machine code for a 32-word compute
shader (`shl.b` + `stib`), and `CheeseburgerGpuCompute540.h` emits sagit's
compute dispatch (CS config, shader object, SSBO descriptors, NDRANGE, CP
`0x33`, `flush(4)`). On hardware the stream fences (`rc=0`, seq 9..12,
words=360), but a probe that writes `0xdeadbeef` into a private 4 KiB SSBO
reads back zero, and the scanout band still holds `ff000000`. The GPU reports
bit 30 busy after the dispatch while the later user submission still works, so
the CP accepted the dispatch but the shader did not produce observed writes.
The next step is a completion delay plus a state-variant matrix (WGID/UNK 0,
thread size, control bits, single-thread dispatch) in one boot.

## Compute blocker (P21-Lapwing/Petrel/Plover)

Seven CS state variants (sagit baseline, WGID/UNK 0, thread size 0, no
0x2/BUFFER, single thread, SSBO block 14, NUM_UNIT 1) all fence but write
nothing, including into a private 4 KiB SSBO and after a 20 ms delay. The boot
log shows `after=140000/140001` before reset but `rbccu=778001/1 sp=778001/1`
after ZAP: the core domains fall back off, which 2D does not need but a CS
does. A sagit-style quiescent halt/resume of those domains (P21-Petrel/Plover)
either failed its own idle check or wedged the system; the halt path was removed
and P21-Sandpiper control-booted the restored baseline (2D clear match=4/4,
user chain err=0, automatic return). The current tree never halts the live CP.

## GPU-to-GPU copy (P21-Starling)

The finished 256x64 image is copied with sagit's sourced `CP_BLIT`
(`copySetup`/`copyTile`/`copyEnd`) into two private linear targets: one at the
source pitch (1024) and one at a different 64-byte pitch (1088). Both return
all four quadrant colours on hardware (`am=4/4`, `bm=4/4`, boot `0x40a85c75`),
so the snapshot2D primitive works for surface-to-surface handoff. The GOP
scanout (pitch 4320) remains outside the 2D/3D engines.

## Full-frame MDP attempt (P21-Veery)

An 8 MiB 1088x1920 frame was requested at probe start (63.9 s) and retried
eight times: no contiguous block below 4 GiB was available, so the MDP flip
was skipped (`no low contiguous 8 MiB frame`) and the panel stayed on the
firmware buffer. The 2D clear and GPU-to-GPU copy remained 4/4. With MDP
direct scanout dependent on a low 32-bit frame, the next handoff target is the
compositor IOSurface the display already receives and copies.

## Memory model correction (P21-Serin)

The earlier low-pool workaround came from a misattribution: a copy test wrote
past its 64 KiB destination (pitch 1088 x 64 needs 69632 bytes), stalled the
SMMU context and made every later test and the client open fail closed. With
the destination sized by pitch*height and sagit-style normal scattered pages
(no low mask, no contiguity), a 32 MiB buffer landed entirely at 5.27-5.32 GiB
and the 2D engine wrote its four quadrants with `match=4/4`; the client chain
also returned (`GPSVC open=2 sub=1 fence=1 err=0`, `GBOD`). The GPU does not
require low physical memory; only MDP direct scanout is limited to 32-bit
physical addresses.

## High-address closure (P21-Redpoll)

With the scattered-page policy, a 32 MiB buffer occupied 5.27-5.33 GiB. The
2D engine wrote its four quadrants (`match=4/4`), an IB placed at
`pa=0x153d49000` was fetched by the CP and executed (`sent=5a5a0001/2`), and a
low IB read a high page with `CP_MEM_TO_MEM` (`val=1234abcd`). The client chain
ran normally (`GPSVC open=2 sub=1 fence=1 err=0`). Low physical memory is not a
GPU requirement; only MDP direct scanout keeps its 32-bit SRC0 limit.

## Window and low-pool cleanup (P21-Siskin)

The low pool and every low-address branch were removed. The client IOVA window
is 128 MiB at 0x4000000 and the SMMU aperture is 256 MiB (leaf budget 65536,
range ledger 4096), matching sagit's IOVA scale rather than the earlier
16 MiB test window. P21-Siskin keeps the 2D clear/copy, the 5.14-5.32 GiB
high-address CP fetch/read tests and the client chain (GPSVC open=2, sub=1,
err=0) working on the enlarged aperture.

## Batched scattered mapping (P21-Twite)

The 4K kit's `ArmSmmu4KLiveUpdateContextBatch` is now reachable through
`cheeseburger_gpu_smmu_map_batch`/`unmap_batch`, chunked at 256 runs per
transaction. An 8 MiB 1088x1920 BGRA buffer (pitch 4352) was allocated as
normal pages, mapped as 2040 physical runs at 0x5000000, and filled with four
1088x480 bands by the 2D engine (`match=4/4`, seq=13) while the client chain
stayed healthy. The service still maps per run; switching its BO path to the
batch API and adding sagit's 16 MiB/BO, 128 MiB/client, 192 MiB global quotas
is next.

## Service batch mapping and quotas (P21-Wheatear)

The service BO path now collects every physical run and calls the kit's batch
mapper/unmapper instead of one live update per run. sagit's native limits are
enforced: 16 MiB per BO (alloc and import), 128 MiB per client, and Query
reports the 16 MiB cap while the address window remains 128 MiB. The 8 MiB
surface test moved to 0xC000000, outside the client window. P21-Wheatear keeps
the clear/copy/high-address tests and the client chain (GPSVC open=2 sub=1
err=0, GBOD) intact.

## Compositor surface handoff (P21-Wryneck)

After the display validates a compositor IOSurface and before any copy/scale/
flip, the kernel maps the surface's first 64 rows at 0xD000000 and the 2D
engine draws a 256x64 quadrant pattern. On hardware the surface stride was
5120 (64-byte aligned), 80 physical runs spanned 4.3-5.98 GiB, and the CPU
read the four quadrants back 4/4 (`SURF rc=0 seq=23`); the display then
presented that same surface through its existing CPU copy. This is a
GPU-to-compositor write, not yet per-frame GPU composition or Metal.

## Per-frame compositor handoff (P21-Yellowlegs)

P21-Xenops made that handoff run on every validated surface swap: map the
first 64 rows at 0xD000000, draw a moving 256x64 block with rotating colours,
fence, then unmap the range so the ledger only holds the current frame. The
first attempt panicked with a kernel data abort at pc 0xfffffff00bfa4fd8
(far 0xfffffff82e7be000, ESR 0x96000007). Symbolizing the candidate kernel put
the fault on `ldr w11,[x8]` inside the empty-IB scan of
`cheeseburger_gpu_engine_submit`; x8 was the boot-global `cb_inline_ib`, whose
client IB buffer had been freed, so its kernel mapping was gone. The per-frame
path did not touch that pointer itself: every `clearKick` call entered the same
scan and read the stale global. The engine now takes the first IB's kernel view
as a call argument; the service passes it only after the job's holds exist, and
board-internal callers pass none. P21-Yellowlegs (boot 0x447ff06e) then ran the
per-frame handoff on hardware: `SURF f=1 rc=0 seq=23 w=491 runs=80 stride=5120
match=4/4` at 206.6 s, six `CB DISP surface paint rc=0` swaps through 297 s, the
frame counter reached 27 by the 338 s snapshot, no panic occurred, all earlier
tests stayed green, and the 400 s path returned the device to Recovery (427 s
after boot). The remaining edge is that a failed fence still unmaps the
frame's range; that should become fail-closed next.

## GPU readback of live UI pixels (P21-Zenaida)

The first attempt to render real UI content (P21-Yellowhammer) copied a window
of the surface into another position of the same surface. It booted and
returned after 427 s, but every frame mapped 256 rows as 319 single-page runs
and the mapper logged three lines per run, so the persistent window kept only
the last ~165 s and the f=1 readback was lost; the snapshot's 0/4 could not be
attributed. P21-Zenaida keeps the 64-row band, copies a 512x64 window of the
surface's own pixels into the separate 8 MiB GPU surface at 0xC000000, quietens
the per-map success logs, and retires the frame mapping only after a proven
fence. On hardware (boot 0x40972449) frame 1 at 202.3 s reported
`CB GPU surf: f=1 rc=0 seq=23 w=353 runs=80 stride=5120 src=ff010000×4
dst=ff010000×4 match=4/4`: the GPU read the live compositor surface and wrote
the same pixels into its own surface. The sampled region was a flat colour, so
this proves the read/copy geometry, not arbitrary content variation; sampling
a region with UI detail is the next step. Six painted swaps followed through
345 s, the client chain stayed err=0, and the 400 s path returned the device
to Recovery at 432 s.

## Display-bank SMMU hand-off (P21-Shelduck)

sheng's display module presents through a stage-1 window of the display bank
(`sheng-dpu-scanout=2`): the display pipe fetches the compositor surface by
IOVA, the flip waits for that frame's GPU fence, and a failed map/latch falls
back to the CPU copy. Our tree only had a physical-address flip, which cannot
take an 80-run surface above 4 GiB. The MSM8998 device tree offers the same
mechanism: `arm,smmu-mmss@cd00000` with `qcom,smmu_mdp_unsec_cb` (SID 0) and
`qcom,smmu_mdp_sec_cb` (SID 1), separate from the GPU's kgsl SMMU at 0x5040000.

P21-Shelduck added the first migration step: a guarded, identity-only takeover
that programs a context through the vendored ArmSmmu4K kit, identity-maps the
firmware buffer, re-commits the pipe that already scans it, and restores every
register. On hardware (boot 0x3b6fa866) the guard refused at 191.6 s:
`SCTLR=0x200626` (M=0), `SMR0=0x80000000`, `S2CR0=0` — the bootloader
pre-staged SID 0's route to context bank 0 but left translation disabled, so
the GOP is currently fetched physically. Nothing was written and the system ran
normally (`SURF f=1 ... match=4/4`, client err=0, automatic return at 434 s).
The next step is to use a free context bank instead of bank 0, keep SMR0 and
only repoint S2CR0.CBNDX, with the same identity-first rollback discipline.
`flippath::present` also now rejects a physical address above 32 bits instead
of truncating it.

P21-Godwit landed the full sheng-style path behind an explicit
`cheeseburger-dpu-scanout=1`: a free MMSS context bank is programmed with the
same SMMU-v2 sequence the GPU SMMU proved (TCR/TCR2 SEP 7, CB SCTLR 0x1027,
ACTLR, MAIR), the firmware buffer is identity-mapped, S2CR0 is repointed while
SMR0 is preserved, and same-size BGRA frames are mapped into two fixed 16 MiB
IOVA windows that the pipe flips to; scaling frames or any failure return the
pipe to the firmware buffer for the CPU copy. Without the opt-in the module
only reads SCTLR/SMR0/S2CR0 and writes nothing. Two Godwit boots did not
validate the path: the first rejected the 4320-byte GOP stride under a wrong
64-byte check (MDP needs only 8-byte alignment), and the corrected boot
returned at 433 s but its persistent log stopped near 192 s with
`DISPLAY frames=0`, before any validated swap, so the takeover never ran. The
read-only probe remains the verified baseline; the next run enables the opt-in
and moves the takeover before the first compositor swap. Follow-up runs did not get that far: a Willet boot that executed the identity check failed its table-pool allocation (`rc=-6`, the allocator budget was too small), and a later boot stopped right after GPU reset (~100 s, display clients 0) before any test. The user reported the gated Godwit image (takeover active) as a black screen. The takeover source was therefore rolled back to the verified read-only probe; the full implementation remains in git history for a later staged retry.

## Why this shape

- sagit and the OnePlus 5 are both MSM8998/A540, so the 2D state and the CP
  packets are the same hardware contract. The board-dependent parts (power,
  clocks, SMMU, firmware, ring) remain this port's own, already verified code.
- The ABI has no per-job resource list, so the service holds every mapped BO
  of the client until the job's fence. That is the safe superset for IB data,
  textures and write targets.
- A5xx has no Turnip backend. This 2D engine is the first real graphics path
  available without a shader compiler; the next step is the VSC/RB triangle
  path using sagit's `PipelineEncoder` and IR3-generated shaders.
