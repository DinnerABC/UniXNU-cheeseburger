## 必须更正：D 轮 tick 并非本次启动

D 轮 `out/p21/persistent-logs/20261031T130216Z/retrieval.json` 的 boot ID 是 `0x51e9e4e1`。只筛选该 boot ID，记录仅有 `seq=1..5`、`sec=35` 的 `halt/ack/idle/swrst/cm3`；窗口里后续 `tick sec=58..298` 的 boot ID 是 **上一轮 C 的 `0x511b5457`**。因此报告“D 轮 tick 继续到约 370 秒”不受这份回收数据支持，不能由此认定 D 期间内核/UFS 在 cm3 之后仍活跃。旧记录混入问题尚未在展示/判读层彻底解决。

`BootLog.c` 中 periodic、auto-reset、step 分别有各自的静态 seq，但都按同一 `seq % boot_log_hb_count` 选择环槽；不同生产者可能互相覆盖。该事实进一步限制缺失标记的解释。应修正为同一共享序号及可证明的同步协议，或固定分区/分配槽位，并让读取工具严格按当前 boot ID 过滤；记录覆盖、写失败及环容量。修复必须离线测试并保留旧版原始窗口，不改变日志分区边界。

D 轮最后同 boot 标记 `cm3` 发生在 TrustControl 清除前附近；标记后还有读取检查等代码。没有 `trust` 标记并不足以唯一定位阻塞指令，且该版只在写/读后打标。E/F 未启用 clear 时完成并自动回收是强相关证据，支持继续保持该开关关闭，不足以证明 D 一定卡在 TrustControl 写、读或安全世界控制；亦不能排除其他配置差异。拆分前置/写后/读后标记的新版需用安全实验验证，但不应重新执行危险 clear 来强行验证。

## 决策：先 A 的只读部分 + D 的源码取证，推迟 B 和 C

1. **先离线修心跳及证据归属**：共享环并发/覆盖、boot ID 过滤、旧记录来源和失败计数；用 host 测试覆盖跨 boot、槽位覆盖、多生产者、溢出和乱序，并重新解析 A–F。只提交源码、工具和测试，不触碰原始日志。更新 INDEX，核对 F 的 manifest 和 pins。
2. **并行做只读源码取证（不意味着要开子代理）**：逐项核对本机 vendor DT、Linux msm8998 GPU SMMU 的 stream/SMR/S2CR/CB 路由、位宽、TTBR 寄存器访问宽度、CP/GPU 安全属性、实际日志的输出格式。核对 0x1027/0x1167 对应实现版本的定义；不要因 lack of fault 断言没有发起访问。对照 sagit 原始实现与本机内核/板级差异，列出来源与证据等级。
3. **A 先做纯观测，不加额外硬件改写**：只读分开打印 TTBR0/S2CR 原始 32 位值、预期物理地址、各级 PTE 和地址范围，同时确认 trace 是同一启动快照及真实源码版本。先完成当前 PTE walker 的宿主测试。将 64 位 TTBR 写入视作独立实验：首先从同 SoC 参考确认寄存器宽度、对齐、写序、副作用和当前 bank 处于可安全操作状态，再按授权独立评估，不能归入“只读低风险”。
4. **暂缓 B**：`0x1167` 改变 fault 控制，可能改变故障处理和阻塞行为；必须先搞清每个 bit、故障捕获及恢复路径，且一项一项地进行。F 轮一次健康不证明 full-start 普遍安全。
5. **暂缓 C**：先完成 D 中安全状态及固件链前提的证据；如确有需要，再提出完整官方机制、硬件版本、授权边界与可审查设计。禁止强制 TrustControl 写或绕过安全机制。当前 `cheeseburger-gpu-trust-clear=1` 是显式危险入口，不应启用。
