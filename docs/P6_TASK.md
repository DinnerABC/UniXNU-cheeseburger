# UniXNU-cheeseburger P6：XNU 早期初始化攻坚、自动化诊断与 iOS 引导准备

## 0. 总目标

项目目录：

`/Volumes/NAS-MacData/Project/IOS/UniXNU-cheeseburger/`

目标设备：OnePlus 5 / cheeseburger / Snapdragon 835 / MSM8998。

当前已取得 XNU `__start` 实机执行证据，但入口之后停机。

**本轮必须从 XNU 入口向前推进，不再以编译成功、UEFI 菜单运行、DarwinBoot 装载或者入口色条作为主要成果。**

优先目标：

1. 让 XNU 通过早期汇编初始化。
2. 完成 MMU、启动页表、栈和 BootArgs 初始化。
3. 进入 ARM64 内核 C 初始化。
4. 尝试完成 CPU、VM、Platform Expert 初始化。
5. 进一步推进 IOKit 和根存储设备识别。
6. 同步准备 iOS 根卷镜像，条件满足后尝试进入用户空间。

本轮允许长时间连续执行本地源码修改、增量编译、静态测试和有限次数的实机启动测试。不使用 GitHub Actions。

不要仅完成一个小任务便停止。遇到能够自行解决的问题，应持续定位、修复、编译、验证。

## 2. 主线 A：XNU 早期汇编启动

这是最高优先级。

### A1. 建立精确的入口执行地图

定位固定版本 XNU 的：

- `osfmk/arm64/start.s`
- `__start`
- 启动页表构造；
- MMU 启用和地址空间切换；
- 栈初始化；
- BootArgs 读取；
- 第一次进入 C 函数；
- ARM64 初始化后续调用链。

结合真实编译的 Mach-O、符号表、反汇编及链接地址建立执行流程。

确认入口处的色条到底位于哪条指令之后。

不得仅通过源码推测实际执行位置；需要核对最终链接二进制。

### A2. 分段诊断内核启动

在关键位置增加轻量级入口标记，例如：

- S00：已进入 `__start`；
- S01：BootArgs 指针有效性检查；
- S02：进入页表构建；
- S03：页表构建完成；
- S04：准备 MMU 配置；
- S05：MMU 开启前；
- S06：MMU 开启后；
- S07：虚拟地址空间切换完成；
- S08：栈可用；
- S09：第一次 C 函数入口；
- S10：ARM64 初始化继续执行。

这些是待实现的诊断点，不代表已完成。

优先使用少量可区分的状态编码、屏幕图形或已验证的日志输出。

特别注意：

- MMU 开启前后 framebuffer 地址的可访问性可能变化；
- 诊断代码不能破坏启动寄存器；
- 不得在栈建立前调用需要栈的函数；
- 不得在 MMU 切换窗口访问尚未映射的地址；
- 不得破坏通用寄存器保存约定；
- 不得使诊断探针本身成为新的异常源。

先通过静态反汇编验证每个插桩位置，再做实机测试。

不要一次性在几十个位置插入复杂代码。

采用逐级定位或二分式插桩缩小故障范围。

### A3. 页表与 MMU 验证

重点检查：

- `TCR_EL1`
- `TTBR0_EL1`
- `TTBR1_EL1`
- `MAIR_EL1`
- `SCTLR_EL1`
- `VBAR_EL1`
- `CurrentEL`
- BootArgs 虚拟与物理地址；
- 内核 Mach-O 加载地址与虚拟地址；
- kernel slide；
- 页表内存池容量；
- 4 KiB granule；
- 内存属性与对齐；
- 设备保留内存；
- exception vector 映射。

复用 UniXNU 官方的：

- `native-4k-bootstrap-capacity`
- 4 KiB granule 校验工具；
- 物理地址宽度相关补丁；
- QEMU entry fixture。

这些必须与当前 XNU 固定版本和实际启用补丁核对，不得重复叠加补丁。

如需修改 XNU，只修改最小必要实现。

### A4. 异常捕获

在可行情况下建立适合当前启动阶段的异常向量与最小 fault 记录。

重点收集：

- Exception class；
- ESR_EL1；
- FAR_EL1；
- ELR_EL1；
- SPSR_EL1；
- SP_EL1；
- PC/LR；
- 当前执行阶段；
- 相关页表或内存属性。

不得假定异常发生后一定能够绘制 framebuffer 或通过 USB 输出。

如果异常处理代码本身尚不可用，应区分“未收到异常日志”和“没有发生异常”。

## 3. 主线 B：CPU、VM 与平台初始化

一旦证明 MMU 开启并进入内核 C 初始化，继续推进：

- `arm_init`；
- 物理和虚拟内存管理；
- pmap；
- CPU 初始化；
- 异常和中断控制；
- ARM Generic Timer；
- PSCI；
- Platform Expert；
- IORegistry 初始化；
- ArmCpu；
- ArmDTPlatform；
- Crypto Bootstrap。

P4 已将真实 timer 路由改为 PPI19，必须验证其在内核实际中断控制器初始化之后的行为，而不是只检查静态配置。

先使用单核启动进行验证（仅在现有平台实现支持时），必要时再引入多核。

针对不同故障建立独立、可回滚的最小补丁。

不要过早开发 GPU、Wi-Fi、蓝牙、音频或摄像头驱动。

## 4. 主线 C：自动化诊断和恢复

继续使用现有自动化控制器，不得重新开发一套重复框架。

目标：

`BUILD → VALIDATE → FASTBOOT BOOT → OBSERVE → COLLECT → CLASSIFY → NEXT TEST`

需要完善：

1. 镜像与设备身份校验；
2. 自动进入 Fastboot；
3. 临时启动；
4. USB 状态监测；
5. 屏幕诊断标记版本标识；
6. 错误分类；
7. 自动保存日志；
8. 可恢复状态下的自动回到 Android；
9. 失联安全停止。

对内核 EBS 后挂死，普通 BootServices 定时器不能保证恢复。

优先研究：

- 已有 P3Probe；
- 串口 UART；
- 可验证的 USB 日志通道；
- 安全可用的 panic buffer；
- 经实测可用的持久日志存储；
- 外接诊断硬件。

跨重启日志不能依赖未经验证的易失内存保持。

如无可靠自动回收途径，可用屏幕状态标记及用户一次性拍照作为阶段证据，但必须保留证据来源说明。

不得通过未经验证的 watchdog 寄存器写入、EDL 或无限电源循环制造所谓自动恢复。

避免重复测试相同哈希、相同配置且已知必然挂死的镜像。

## 6. 实机测试策略

使用两级测试。

### 一级：无实机风险的离线测试

自动完成：

- 反汇编；
- Mach-O 校验；
- ADT 宿主解析；
- 早期页表静态分析；
- 关键寄存器配置验证；
- 驱动匹配检查；
- BootArgs 数据结构检查；
- CRC/SHA256；
- Boot image 回读；
- QEMU 兼容部分的测试。

尽量通过离线测试排除结构错误。

### 二级：实机增量测试

只有候选通过离线门禁后进行。

每一轮至少记录：

- run_id；
- 源码 commit；
- Patch ID；
- 内核 SHA256；
- Boot image SHA256；
- 入口诊断点版本；
- 最深确认执行阶段；
- 设备返回状态；
- 是否需要人工恢复。

首次实机测试时只改变少量影响入口的因素。

若手机失联，终止该轮后续实机操作，保留屏幕和 USB 证据，等待设备被人工恢复；同时继续不依赖设备的离线工作。

不要把自动化跑通率作为唯一优化目标，真正目标是获得更深的 XNU 执行证据。
